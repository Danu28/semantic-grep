π Customization Guide — how it really works

Pi is a small terminal coding agent whose core is extended through five resource types — extensions, skills, prompt templates, themes, and pi packages — configured by layered settings files, guarded by a project trust decision. This page explains every customization surface and the mechanics behind it, as flow graphs. Everything is distilled from the official docs shipped with pi.

Security reality check — read this first Everything pi loads from a project is code or instructions that can act on your machine. Extensions run with your full permissions. Skills can tell the model to run any command. That is exactly why the project-trust gate (section 3) exists, and why every “where do I put files” answer below is qualified by “after the project is trusted”.

0Mental model — how customization attaches to core overview

One picture to hold the whole thing: pi itself is the engine (TUI + agent loop + session store). You never edit the engine — you attach resources to it from many places on disk, and you steer it with settings. Every later section is a zoom into one spoke.

FIG 0 · the whole system in one flow
pi core — starts once per runreads settings → resolves trust → discovers resources → boots model + TUI + agent loop
▼feeds (2 inputs below)
1 · configurationsettings.json ×2 (global + project) merged → active config that decides defaults, theme, tools, packages… (sec 2)
2 · trust decisiongate in front of everything project-local: trust.json / prompt / defaultProjectTrust (sec 3)
▼trusted run
resource discovery (sec 4)all sources → one loader per type → registries: extensions · skills · prompts · themes (+ models & keybindings are separate config files)
▼loaded into
your pi sessionextensions hook the lifecycle · skills sit in the system prompt as descriptions · prompts expand in the editor · theme colors the TUI · packages bundle any of the above

Six facts explain almost everything:

1 · Global & project

Everything is either ~/.pi/agent/… (applies to all projects) or .pi/… in your project folder (applies only there, and only once the project is trusted).

2 · Project wins

When the same setting exists in both files, the project value overrides the global one; nested objects are merged, not replaced.

3 · Settings point at resources

packages/extensions/skills/prompts/themes arrays in settings are just pointers to more files — relative paths resolve against the settings file they live in.

4 · Discovery ≠ loading

Skills are only described in the system prompt and load on demand (progressive disclosure). Extensions & themes load fully at startup. Prompts load when you type /name.

5 · Trust is the lock

Project .pi resources, .agents/skills, and missing packages stay locked until the trust decision lets them in. Global files are never gated.

6 · Code > config

Extensions (TypeScript) can do anything config can, plus events, tools, UI and providers. When you outgrow JSON, you drop to an extension.

1Where everything lives on disk filesystem

Two trees matter. The global config dir (~/.pi/agent — override with PI_CODING_AGENT_DIR) and the per-project .pi/ dir. Package installs live in sibling caches. Sibling .agents/skills dirs (the cross-harness standard) are also scanned.

Relative paths inside settings are relative to that settings fileIn ~/.pi/agent/settings.json paths resolve against ~/.pi/agent; in .pi/settings.json they resolve against .pi. ~ and absolute paths always work. So "skills": ["~/.claude/skills"] reaches other tools’ skills, and a project can point at "../.claude/skills".

Global vs project is a spectrum, not a wall: the same package can be listed in both files, and packages/trust interplay decides who wins (sections 3 & 9).

2Settings — layers, merge, precedence settings.json

Pi config is plain JSON in two files. The project file overrides the global file, and nested objects merge field-by-field. There is no third layer and no include mechanism — the merge IS the whole precedence story.

▼overlay

▼overlay & merge

▼if trusted

Layer rules worth memorizing
  • Global scalar overridden by project scalar; global object deep-merged with project object.
  • defaultProjectTrust and httpProxy are global-only — project files can’t set them.
  • A project defaultTools replaces the global array (arrays don’t merge).
  • Env vars & flags are a fourth, run-scoped influence: e.g. --session-dir > PI_CODING_AGENT_SESSION_DIR > sessionDir; --tools replaces defaultTools with a strict allowlist.

3The project-trust gate trust.json

Pi treats every project folder as untrusted until proven otherwise. Project-local settings, resources and .agents/skills are simply not loaded until the trust decision passes — this is the security boundary that makes the whole model safe.

FIG 4 · what happens at startup (interactive)
pi starts in a project folderdoes the folder (or a parent) carry .pi/ config · resources · .agents/skills?
▼yes to any — is there a saved decision for this folder or a parent?
trust.json has onepreviously saved via the prompt or /trust — apply it silently
no saved decisionask: “Trust this project?” → yes / yes-remember / no
▼trusted
project unlocksload .pi/settings.json + .pi resources · install missing project packages · run project extensions · scan project .agents/skills
not trustedproject layer ignored for this run; only global config applies
Non-interactive modes never prompt -p, --mode json, --mode rpc skip the prompt and fall back to defaultProjectTrust: ask (default, = ignore project resources) · never (= ignore) · always (= trust). Override per-run with --approve/-a or --no-approve/-na. pi config and package commands use the same flow; pi update never prompts.

The decision flow in one line

Extensions first (sec 8: a project_trust handler can answer for you) → saved trust.json decisions (first match wins) → defaultProjectTrust decides whether pi asks, trusts, or declines.

Save a decision: /trust

Writes ~/.pi/agent/trust.json only (current session isn’t reloaded — restart to apply). Decisions cover the current folder and the immediate parent.

Theme/skill dirs under ~/.pi/agent and ~/.agents are global, never gated. Only the project-scope dots are behind the gate.

5Prompt templates /name in the editor

Markdown snippets that expand into real prompts when you type /name. The filename (minus .md) is the command name, frontmatter carries the description, and positional arguments substitute into the body.

FIG 6 · what happens when you type a slash
editor: you type /autocomplete lists templates: name → argument-hint → description (missing description? first non-empty line is used)
▼submit e.g. /component Button "click handler"
template found: prompts/component.mdloaded from any discovery source (sec 4) — not the live session file, just a file read
▼substitution
arguments applied$1=Button · $2=click handler · $@/$ARGUMENTS=all · ${1:-default} fallback · ${@:N} / ${@:N:L} slices
▼
expanded into the editor as your promptyou can still edit before sending; /review & friends are just text, not commands

Example

---
description: Review staged git changes
---
Review the staged changes (git diff --cached). Focus on:
- Bugs and logic errors
- Security issues
- Error handling gaps

Frontmatter

  • description — optional; falls back to first non-empty line.
  • argument-hint — optional; shown in autocomplete: "<PR-URL>" required vs [instructions] optional.

Discovery recap

  • Global ~/.pi/agent/prompts/*.md, project .pi/prompts/*.md (trusted).
  • Packages: prompts/ dir or pi.prompts in manifest.
  • Settings prompts array, CLI --prompt-template <path>; kill-switch --no-prompt-templates.
  • Subdirs need explicit settings (non-recursive).

6Skills — Agent Skills progressive disclosure

A skill is a folder with a SKILL.md (frontmatter + instructions) plus any scripts/references it needs. Pi implements the open Agent Skills standard (agentskills.io), so skills written for other agents mostly just work. The trick is progressive disclosure: pi never puts full skill bodies in context — only names + descriptions — and the agent pulls a body in when the task matches.

FIG 7 · why skills are cheap to have many of
startup scanall skill sources → extract name + description only (validation warnings tolerated, e.g. bad name/description length; duplicates: first wins; disable-model-invocation: true hides from prompt)
▼
system prompt gets a compact XML index <name> + <description> per skill — maybe 2 lines each, not the whole manual
▼task matches a description → agent reads SKILL.md (via read, or bash) — or you force it
body loaded on demandfull instructions + relative paths to scripts/, references/, assets/ — resolved from the skill dir
▼
agent executes the workflow/skill:name args also works — args are appended to the content as User: <args> (requires enableSkillCommands, default on)

Anatomy & rules

my-skill/
├── SKILL.md          ← required
├── scripts/          ← helper scripts
├── references/       ← deep docs, read on demand
└── assets/
---
name: pdf-tools
description: Extract text/tables from PDFs. Use when…
---
# usage instructions follow…
  • name (required): lowercase a-z/0-9/hyphens, ≤64 chars. Pi is lenient: it doesn’t require name = folder name (the standard does, but that breaks shared skill dirs).
  • description (required): ≤1024 chars, drives when the model loads the skill — be specific.
  • Optional: license, compatibility, metadata, allowed-tools, disable-model-invocation.
  • Malformed/description-less skills warn & skip; unknown fields ignored; root md that isn’t a skill is silently ignored.
  • Reuse other harnesses’ skills: "skills": ["~/.claude/skills", "~/.codex/skills"] in settings.

Sources recap (sec 4): global ~/.pi/agent/skills/ + ~/.agents/skills/; project .pi/skills/ + .agents/skills/ up to git root (trusted); packages; settings array; --skill (loads even with --no-skills).

8Extensions — TypeScript modules on the core full power

An extension is a default-exported factory function that receives the ExtensionAPI. Pi imports it with jiti (TS runs with no build step) and calls it at startup — whatever the factory registers becomes part of the run. This is the escape hatch: events, custom tools the model can call, commands, UI, providers, custom rendering.

FIG 9 · an extension’s place in the run
startupextension file discovered (sec 4) → jiti-imported → default factory called with pi — async factories are awaited before session_start / resources_discover / provider flush
▼
factory registers capabilitiesevent handlers · tools · commands · shortcuts · flags · providers · message/entry renderers · markdown transformers · UI (dialogs, widgets, custom components) · session entries
▼then, for the whole session…
handlers fire on the lifecycle (FIG 10 below)the model can call your registerTool tools; ctx.ui lets you prompt the user (confirm/select/input/notify/setStatus/setWidget); state can survive restarts via pi.appendEntry session entries
What a minimal extension looks like 
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { Type } from "typebox";

export default function (pi: ExtensionAPI) {
  pi.on("tool_call", async (ev, ctx) => {           // intercept: block a tool
    if (ev.toolName === "bash" && ev.input.command?.includes("rm -rf")) {
      const ok = await ctx.ui.confirm("Dangerous!", "Allow rm -rf?");
      if (!ok) return { block: true, reason: "Blocked by user" };
    }
  });
  pi.registerTool({                                  // new tool the model can call
    name: "greet", description: "Greet someone",
    parameters: Type.Object({ name: Type.String() }),
    async execute(_id, params) { return { content: [{ type: "text", text: `Hello ${params.name}!` }], details: {} }; },
  });
  pi.registerCommand("hello", {                      // /hello
    description: "Say hello",
    handler: async (_args, ctx) => ctx.ui.notify("Hello!", "info"),
  });
}
Test one-off with pi -e ./my-ext.ts (no install needed).

9Pi packages share & install

A pi package is any npm/git/local bundle that ships extensions, skills, prompts or themes — declared via a pi key in package.json or via convention directories. pi install downloads it and records it in settings; at the next startup pi installs anything missing. This is how you share a setup or pull in the ecosystem (the pi-package keyword powers the gallery at pi.dev/packages).

FIG 11 · install → record → auto-load loop
npmnpm:pkg@1.2.3 → ~/.pi/agent/npm/ or .pi/npm/ (+npm install deps)
gitgit:github.com/user/repo@v1 or URL → cloned to ~/.pi/agent/git/<host>/<path> / .pi/git/…; refs pinned; SSH keys honored
local pathfile → single extension; dir → package rules. Added to settings, not copied; relative → resolved against the settings file
▼pi install <src> (or -e = temporary for this run only)
recorded in settingsdefault → global settings.json packages array · -l → project .pi/settings.json (team-shareable)
▼next startup (after trust, if project-scoped)
missing packages auto-installedthen resources filtered & loaded (sec 4); pi remove / pi list manage; pi config enables/disables individual resources

Anatomy

{
  "name": "my-package",
  "keywords": ["pi-package"],       // gallery discovery
  "pi": {
    "extensions": ["./extensions"],
    "skills":     ["./skills"],
    "prompts":    ["./prompts"],
    "themes":     ["./themes"]
  }
}

No pi manifest? Convention dirs auto-discover: extensions/ (.ts/.js), skills/ (SKILL.md folders, recursive), prompts/ (.md), themes/ (.json).

Rules that bite

  • Deps: runtime deps in dependencies (installed with --omit=dev). Core packages (@earendil-works/pi-*, typebox) go in peerDependencies — don’t bundle them. Other pi packages must be bundled (bundledDependencies).
  • Filtering: object form in settings — {"source": "npm:pkg", "skills": ["a"], "extensions": []} narrows what loads per type.
  • Scope & dedupe: same package in global + project → project wins unless autoload:false, then project is a delta over global. Identity: npm name / git URL-without-ref / resolved absolute path.
  • Update: pinned npm/git refs are skipped by pi update --extensions|--all, but git clones are reconciled to their pinned ref (reset+clean+install).

10Keybindings keybindings.json

Every shortcut is an action with an internal namespaced id (e.g. tui.editor.deleteWordBackward, app.model.cycleForward) and one or more default keys. You rebind by id in ~/.pi/agent/keybindings.json; user bindings replace defaults for that action. That’s the entire mechanism — ids, not key names, are the API (extension authors use the same ids).

FIG 12 · key → action resolution
keystroke arrivesterminal reports key (+ modifiers: ctrl/shift/alt/super)
▼
lookup: which id binds this combo?1 · your keybindings.json overrides (single key or array) → 2 · defaults. Legacy pre-namespaced ids auto-migrate at startup
▼
action runsedit / /reload after changing the file — no restart needed

Format

{
  "tui.editor.historyPrevious": "ctrl+p",              // one key
  "tui.editor.historyNext": ["ctrl+n", "ctrl+j"],      // or several
  "tui.editor.deleteWordBackward": ["ctrl+w", "alt+backspace"]
}

Keys: letters, digits, f1–f12, specials (escape, enter, tab, space, backspace, delete, home, end, pageUp, pageDown, up…), symbols. Modifiers combine: ctrl+shift+alt+x. super needs a terminal that reports it separately (Kitty keyboard protocol) — most won’t.

11Custom models & providers models.json + extensions

Three ways to steer what pi talks to: (1) choose/save among known models, (2) declare local or proxied providers that speak a supported API (Ollama, vLLM, LM Studio, any OpenAI/Anthropic-compatible endpoint) in models.json, (3) implement genuinely new providers or OAuth flows as extensions. Credentials resolve CLI → auth → env → config.

Full model entry options

Per model: id (required) · name · reasoning · input modalities · contextWindow · maxTokens · cost {input,output,cacheRead,cacheWrite}.

Provider level: api in {OpenAI Completions, OpenAI Responses, Anthropic Messages, Google Generative AI} · compat: e.g. supportsDeveloperRole:false, supportsReasoningEffort:false for servers that choke on them (Ollama/vLLM/SGLang) · custom headers via shell commands.

Missing apiKey hides models from /model until you save one with /login or pass --api-key — that’s why local servers get a dummy value.

12Environment variables 3 roles

Env vars play three distinct roles. Mixing them up is the most common source of “why isn’t my var visible?” confusion: process config vars are read by pi at startup; session vars are injected into shell tool commands; markers identify pi as the parent.

FIG 14 · the three roles
① process configread by pi itself at startup: PI_CODING_AGENT_DIR (config dir override) · PI_CODING_AGENT_SESSION_DIR · PI_PACKAGE_DIR · PI_OFFLINE · PI_SKIP_VERSION_CHECK · PI_TELEMETRY · PI_CACHE_RETENTION=long · terminal overrides (PI_HYPERLINKS, PI_IMAGE_PROTOCOL, PI_TRUE_COLOR, PI_TUI_ESC_TIMEOUT, PI_HARDWARE_CURSOR) · VISUAL/EDITOR · HTTP(S)_PROXY
② session env → shell toolsevery bash/powershell tool command starts with: PI_SESSION_ID · PI_SESSION_FILE · PI_PROVIDER · PI_MODEL · PI_REASONING_LEVEL — resolved fresh per command. NOT injected into user !/!! commands
③ process markersset on pi’s own process, inherited by children: AI_AGENT=pi (generic) · PI_CODING_AGENT=true (pi-specific). Tooling uses these to detect they run inside pi
Practical notes
  • Ask “which model am I?” in a shell: printf '%s/%s %s' "$PI_PROVIDER" "$PI_MODEL" "$PI_REASONING_LEVEL" — not from the system prompt.
  • Custom tools made with createBashTool()/createPowerShellTool() expose session env by default; opt out with exposeSessionEnvironment:false (also strips inherited stale values).
  • Provider API keys (ANTHROPIC_API_KEY, OPENAI_API_KEY, cloud creds…) are documented in docs/providers.md, not here.
  • PI_OFFLINE=1 or --offline kills all startup network ops (update checks, package checks, telemetry).

Mental-model recap (30 seconds)

How customization actually works
  1. pi starts → asks/checks trust (sec 3) → merges settings global-then-project (sec 2).
  2. It then discovers resources from dirs + packages + settings + flags (sec 4) — extensions run, skills are indexed, prompts wait for /, themes paint.
  3. During the conversation the extensions listen to events (sec 8, FIG 10), skills load on demand when the task matches (sec 6), and /name expands templates into text (sec 5).
  4. Everything project-scoped stays behind the trust gate; remove trust and a folder reverts to global-only.
