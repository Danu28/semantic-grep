π Extensions — the TypeScript escape hatch

An extension is one default-exported function that receives ExtensionAPI and hooks itself into pi’s run: lifecycle events, custom tools, slash commands, dialogs, widgets, message renderers, model providers. It runs as TypeScript with no build step. Config can only describe pi; code extends it. This page is the whole surface, as flow graphs. Distilled from the official docs/extensions.md and the shipped examples.

0What an extension is — the factory and its powers one function, whole surface

Pi imports your file with jiti (TypeScript runs directly) and calls its default export with the ExtensionAPI. Whatever that factory registers becomes part of the run. A factory can be async; pi awaits it before continuing startup.

FIG 0 · from file on disk to behaviour in a session
discoveryauto-found in ~/.pi/agent/extensions/ & .pi/extensions/ · or pointed at by settings extensions[] / packages[] / CLI -e
▼project-local entries wait for project trust
jiti import → default factory called with pino build step · npm deps resolve from a package.json beside the file · async factories are awaited
▼the factory registers…
event handlerspi.on(event, handler) — react to, block, or transform what pi does
capabilitiestools · commands · shortcuts · CLI flags · message & entry renderers · markdown transformers · providers
runtime controlsendMessage · appendEntry · setActiveTools · setModel · exec · pi.events
▼
session runs with your additions livetools appear in the system prompt & pi.getAllTools() · commands in autocomplete · handlers fire in load order
▼/reload — or ctx.reload() from a command — tears down and runs this whole flow again
session_shutdown → session_start(reason:"reload")close session-scoped resources in shutdown, rebuild in-memory state in start

Three properties define the model:

it’s just codefull system permissions, Node built-ins, any npm package. Nothing is sandboxed — this is why installs are a trust decision (§8).
registration, not patchingyou never edit pi. You call register* / on / send* and pi weaves it in. Every registration in one factory shares one closure — that closure is your extension’s state.
load order mattershandlers run in extension load order; tool_result chains, input transforms chain, before_agent_start system prompts chain. Order is deterministic, and yours to reason about.
A minimal but complete extension 
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { Type } from "typebox";

export default function (pi: ExtensionAPI) {
  // 1 · react to events
  pi.on("session_start", async (_event, ctx) => {
    ctx.ui.notify("Extension loaded!", "info");
  });

  pi.on("tool_call", async (event, ctx) => {
    if (event.toolName === "bash" && event.input.command?.includes("rm -rf")) {
      const ok = await ctx.ui.confirm("Dangerous!", "Allow rm -rf?");
      if (!ok) return { block: true, reason: "Blocked by user" };
    }
  });

  // 2 · register a tool the model can call
  pi.registerTool({
    name: "greet",
    label: "Greet",
    description: "Greet someone by name",
    parameters: Type.Object({ name: Type.String({ description: "Name to greet" }) }),
    async execute(_id, params) {
      return { content: [{ type: "text", text: `Hello, ${params.name}!` }], details: {} };
    },
  });

  // 3 · register a slash command
  pi.registerCommand("hello", {
    description: "Say hello",
    handler: async (args, ctx) => ctx.ui.notify(`Hello ${args || "world"}!`, "info"),
  });
}

Test it without installing: pi -e ./my-extension.ts. For hot-reload, put it in an auto-discovery dir and run /reload.

Async factories, and the resource rule An async default export is awaited before session_start, before resources_discover, and before providers queued with registerProvider() flush — perfect for fetching remote config or discovering models at startup.

But: factories also run in invocations that never start a session. Never start background resources (processes, sockets, watchers, timers) from the factory. Start them in session_start or on first use, and register an idempotent session_shutdown handler that closes them.
// async factory: discover models from a local server before startup completes
export default async function (pi: ExtensionAPI) {
  const { data } = await (await fetch("http://localhost:1234/v1/models")).json();
  pi.registerProvider("local-openai", {
    baseUrl: "http://localhost:1234/v1",
    apiKey: "$LOCAL_OPENAI_API_KEY",
    api: "openai-completions",
    models: data.map((m) => ({
      id: m.id, name: m.name ?? m.id, reasoning: false, input: ["text"],
      cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 },
      contextWindow: m.context_window ?? 128000,
      maxTokens: m.max_tokens ?? 4096,
    })),
  });
}

Input processing order — where input sits
  1. Extension commands (/cmd) checked first — if found, the handler runs and input is skipped
  2. input fires — intercept, transform, or handle
  3. Not handled → /skill:name expands to skill content
  4. Not handled → /template expands to template content
  5. Agent processing begins (before_agent_start, …)

3ExtensionContext & CommandContext your ctx

Every handler receives ctx. Event handlers and tools get ExtensionContext; slash commands get ExtensionCommandContext, which adds session-control methods that would deadlock if called from an event handler.

▼commands only

Details worth knowing

  • ctx.signal is usually defined during tool_call, tool_result, message_update, turn_end — and undefined in idle/session/command contexts.
  • ctx.getSystemPrompt() reports pi’s system prompt string, not the final provider payload — it won’t show before_provider_request rewrites.
  • ctx.shutdown() is deferred until idle in interactive/RPC, a no-op in print mode; it emits session_shutdown first.
  • ctx.scopedModels mirrors /scoped-models (from --models + enabledModels); empty = all available. Build model pickers from it, not from the full catalogue.
  • Use CONFIG_DIR_NAME, not a hardcoded ".pi", when building project config paths.

Session control (commands only)

  • newSession / fork / switchSession take a withSession(ctx => …) callback that runs after the replacement session is live.
  • navigateTree(targetId, opts) drives /tree navigation.
  • Discover sessions with the static SessionManager.list(cwd) / listAll().
  • await ctx.reload() = /reload — treat it as terminal for that handler.
Session-replacement footguns
  • withSession runs only after the old session emitted session_shutdown and the new extension instance already got session_start.
  • It still executes in the old closure — your session_shutdown cleanup has already run.
  • Captured old pi, old ctx, and extracted objects (e.g. const sm = ctx.sessionManager) are stale and will throw. Use only the ctx passed to withSession.
  • Carry across only plain data: strings, ids, serialized config.
// safe handoff: capture a plain string, re-send it from the new session’s ctx
pi.registerCommand("handoff", {
  handler: async (_args, ctx) => {
    const kickoff = "Continue from the replacement session";
    await ctx.newSession({
      withSession: async (ctx) => { await ctx.sendUserMessage(kickoff); },
    });
  },
});

4The pi.* API surface everything you can register or do

One object, grouped by intent: subscribe, talk to the session, persist, register UI/commands, drive the runtime, add providers. Most registrations work at load time and later — inside session_start, a command, or any handler — taking effect immediately without /reload.

Messages & persistence — three destinations, don’t mix them

FIG 4 · where your content ends up
pi.sendMessage({ customType, content, display, details }, { deliverAs, triggerTurn })→ into LLM context (custom role). Render it in the TUI with registerMessageRenderer(customType, …).
pi.sendUserMessage("text" | content[], { deliverAs, expandPromptTemplates })→ a real user turn. Always triggers a turn. While streaming you must pass deliverAs.
pi.appendEntry(customType, data)→ session history, never sent to the LLM. Durable across restarts. Render with registerEntryRenderer(customType, …).

Delivery modes (deliverAs)

  • "steer" (default) — queued while streaming; delivered after the current turn finishes its tool calls, before the next LLM call.
  • "followUp" — waits until the agent has no more tool calls.
  • "nextTurn" — queued for the next user prompt; interrupts nothing.
  • triggerTurn: true — if the agent is idle, start a response immediately (only for steer/followUp).

Command provenance

const cmds = pi.getCommands();
// { name, description?,
//   source: "extension" | "prompt" | "skill",
//   sourceInfo: { path, source, scope:
//     "user"|"project"|"temporary",
//     origin: "package"|"top-level", baseDir? } }

sourceInfo is the canonical provenance — never infer ownership from the name. Built-in interactive commands (/model, /settings) aren’t listed. Duplicate command names are kept with suffixes /review:1, /review:2 in load order.

5Custom tools & dynamic tool loading scale past the prompt

Tools are the single biggest extension surface — pi.registerTool() with a typebox schema, execute(), interception events, custom rendering, remote operations. That’s covered in depth by its own page. What’s extension-specific is the scale trick: register a thousand tools, keep a handful active, load more on demand.

Read this next pi-tools.html — FIG 2 anatomy of a tool, interception (tool_call/tool_result), overriding built-ins, remote execution via operations, truncation to 50KB/2000 lines, renderCall/renderResult, withFileMutationQueue for parallel-safe file writes, and state in details.

Dynamic tool loading — a loader tool that switches capabilities on

FIG 5 · register everything, activate a little, add on demand
1 · register every toolall land in pi.getAllTools() — but holding every definition in the system prompt is what you’re avoiding
▼
2 · keep only the loader activesearch_tools active; lookup_weather, search_issues, … inactive
▼a task needs a dormant capability
3 · loader calls pi.setActiveTools([...current, ...matches])must be additive — don’t remove active tools in the same call. Unknown names are ignored. Match by keyword, BM25, embeddings, remote catalog…
▼
4 · pi records which tools were added on that tool resultno special return value needed — the active-set change is the signal
▼

fallback — every other modelpi simply sends the full active list next request. Works everywhere; adding definitions may invalidate the provider’s cached prefix.
Cache-aware rules for loaders
  • Keep the loader tool active for the whole session; prefer adding over replacing. Removals work but never use deferred loading.
  • A lazily loaded tool with promptSnippet/promptGuidelines rebuilds the system prompt when activated — that can break the prefix cache even on capable models. Lazy tools should rely on their description alone.
  • Opt a verified proxy into native handling only when it truly supports it: compat.supportsToolReferences: true (anthropic-messages) or compat.supportsToolSearch: true (openai-responses / openai-codex-responses).
// the shape of a loader (full version: examples/extensions/dynamic-tools.ts)
pi.registerTool({
  name: "search_tools",
  description: "Search for and enable tools relevant to a task",
  promptSnippet: "Search for additional tools when the active tools cannot perform the task",
  promptGuidelines: ["Use search_tools when a task requires a capability that is not currently available."],
  parameters: Type.Object({ query: Type.String() }),
  async execute(_id, params) {
    const matches = /* score pi.getAllTools() against params.query */;
    const active = pi.getActiveTools();
    const added = matches.filter((n) => !active.includes(n));
    pi.setActiveTools([...new Set([...active, ...added])]);
    return { content: [{ type: "text", text: `Loaded tools: ${added.join(", ")}` }], details: { added } };
  },
});

pi.on("session_start", () => {
  // searchable tools stay registered but inactive; loader stays on
  pi.setActiveTools([...pi.getActiveTools().filter((n) => !SEARCHABLE.has(n)), "search_tools"]);
});

class VimEditor extends CustomEditor {   // extend CustomEditor, not Editor
  private mode: "normal" | "insert" = "insert";
  handleInput(data: string): void {
    if (matchesKey(data, "escape") && this.mode === "insert") { this.mode = "normal"; return; }
    if (this.mode === "normal" && data === "i") { this.mode = "insert"; return; }
    super.handleInput(data);             // app keybindings + text editing
  }
}

7State, persistence & branching what survives what

Three kinds of memory, three lifetimes. Pick by asking: should the model see it, should the user see it, and should it survive a fork? Branching is the trap — a naive in-memory variable replays a fork’s history into the wrong state.

FIG 6 · three lifetimes of extension state
in-memory variables in the factory closurefine within one run. Lost on reload, resume, fork, and process exit. Use for caches and handles, never as your only copy of user-visible state.
tool-result detailsthe documented home for state. Rides the session, so branches carry it correctly. Rebuild on session_start by scanning the branch’s toolResult messages.
pi.appendEntry(customType, data)durable session entries, invisible to the LLM. Restore by scanning entries with matching customType. Ideal for TUI-only state (cards, counters, UI config).
export default function (pi: ExtensionAPI) {
  let items: string[] = [];                       // fast working copy

  pi.on("session_start", async (_e, ctx) => {     // rebuild from the branch you’re actually on
    items = [];
    for (const entry of ctx.sessionManager.getBranch()) {
      if (entry.type === "message" && entry.message.role === "toolResult"
          && entry.message.toolName === "my_tool") {
        items = entry.message.details?.items ?? [];
      }
    }
  });

  pi.registerTool({
    name: "my_tool",
    // …
    async execute(_id, params) {
      items.push("new item");
      return {
        content: [{ type: "text", text: "Added" }],
        details: { items: [...items] },             // snapshot so the branch can rebuild it
      };
    },
  });

  pi.on("session_shutdown", async () => { /* close pools, watchers, child processes */ });
}
Reads you’ll use to rebuild state ctx.sessionManager.getEntries() (all) · getBranch() (current branch) · buildContextEntries() (active branch with compaction applied) · getLeafId() · getLabel(entryId). Labels you set with pi.setLabel() persist and show in /tree — use them as named checkpoints.

8Modes, errors, trust & safety where extensions don’t run the same

The same extension runs in four modes, but only interactive mode has a terminal. Guard accordingly, fail safe, and remember that installing an extension is granting it your shell.

Mode matrix

Modectx.modehasUINotes
Interactive"tui"truefull TUI
RPC --mode rpc"rpc"truedialogs/notify over JSON; custom() → undefined
JSON --mode json"json"falseevent stream; UI methods no-op
Print -p"print"falseextensions run, can’t prompt

ctx.mode === "tui" → terminal-only APIs (custom(), component factories, raw key handling). ctx.hasUI → dialogs + notify/status/widget (work in TUI and RPC).

Error handling rules

  • Extension errors are logged; the agent continues. A throwing handler never kills the session.
  • tool_call errors block the tool — fail-safe by design, so a broken guard denies rather than permits.
  • Throw to fail a tool. A thrown execute() error is caught, reported to the LLM with isError: true, and the run continues. Returning a value never sets the error flag.
Security Extensions run with your full system permissions and arbitrary code execution. Install only from sources you trust. Project-local .pi/extensions load only after project trust — that gate exists precisely because of this.

The 30-second summary
  1. Export a default function (pi: ExtensionAPI); drop it in ~/.pi/agent/extensions/ or .pi/extensions/; edit + /reload.
  2. pi.on(event, handler) to observe, block, or transform the run — tool_call and tool_result are the workhorses.
  3. pi.register{ Tool, Command, Shortcut, Flag, Renderer, Provider } to add capability; anything shared lives in the factory closure.
  4. Store state in tool-result details (branch-safe) or appendEntry (durable, TUI-only); rebuild in session_start.
  5. Guard with ctx.mode/ctx.hasUI, pass ctx.signal to async work, close resources in session_shutdown.
