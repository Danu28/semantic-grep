π Tools — built-ins, custom tools & how the loop really works

Tools are the model’s hands: functions it can call mid-conversation (read files, run commands, hit your API). Pi ships eight built-ins and lets you register unlimited custom tools from extensions — with schema validation, interception events, custom TUI rendering, remote backends, and even tools that load other tools. This page is everything about that, as flow graphs. Distilled from the official docs (extensions.md, usage.md, environment-variables.md).

0The tool loop — how a call becomes a result the core mechanic

Everything tool-related is one cycle, repeated until the model stops calling tools. Pi orchestrates: it validates arguments against your schema, fires interception events, executes (in parallel when possible), hands the result back as context, and lets the model decide whether to call again.

FIG 0 · one assistant turn, expanded
model streams a message… and emits a tool calla structured request: toolName + typed arguments
▼
pi validates & preflightsarguments checked against the tool's parameters schema (typebox) · optional prepareArguments ran first · sibling calls in one message preflight sequentially, then run concurrently
▼
tool_execution_start → tool_callinterception point #1 — inspect, mutate arguments, or block (permission gates live here)
▼
execute() runs your codestream progress via onUpdate · watch signal for cancellation · can call pi.exec, hit APIs, spawn anything
▼
tool_execution_update … → tool_result → tool_execution_endinterception point #2 — read, patch or replace the result (middleware chain)
▼result = content (text the LLM reads) + details (structured, for UI & state) + flags
result appended to contextcontent shown to the model; details rendered by the tool row in the TUI (or stored for state)
▼does the model call another tool? (loop) — or answer?
calls againcycle repeats; each tool call in a message may run in parallel with its siblings
no more callsturn ends → agent continues (follow-ups, compaction, next user prompt)

Three layers decide what a tool is, in order of power:

selectionsettings defaultTools + CLI --tools/--exclude-tools/--no-* choose which of the built-ins start active
registrationextensions call pi.registerTool(); SDK embeds via customTools — all appear in pi.getAllTools() with sourceInfo (builtin | sdk | extension source)
executionthe active tool set is what the model sees in its system prompt + API schemas each request
One mental model to keep content = what goes into the model's context (text). details = structured data that does not go to the model, used for TUI rendering and session state. Confusing the two is the most common custom-tool bug — see §2.

1Built-in tools & selecting what’s active the eight

Pi’s own tools cover the coding loop: inspect (read, grep, find, ls) and mutate (edit, write) files, run commands (bash, or powershell on Windows). You can reimplement or wrap any of them — and you can switch the active set per run.

FIG 1 · the built-in set and how to filter it
all configured toolsbuilt-ins (below) + everything extensions/SDK registered (active or not)
▼filters applied in this order…
defaultTools (settings)initial built-ins when omitted → standard set. Project defaultTools replaces the global array. [] starts with none.
--tools <list> / -tstrict allowlist — replaces everything, built-ins and extension tools
--exclude-tools <list> / -xtdisable specific tools from the resulting set
--no-builtin-tools / -nbt · --no-tools / -ntdrop built-ins (keep extension tools) · drop everything
▼
active tool set → offered to the modelre-shapeable at runtime by extensions: pi.setActiveTools(names) (§8)
ToolDoesNotable behavior
readread files (text & images)truncated to 50KB/2000 lines by default; extension read replaces it
edit / writeprecise text replacement / create or overwrite filesboth join a per-file mutation queue so parallel calls can’t clobber each other — custom file tools should too (§9)
bash / powershellrun shell commandschoose per OS (powershell on Windows); spawns get PI_SESSION_ID, PI_PROVIDER, PI_MODEL… env (§5); supports remote ops & spawn hooks
grep / find / lssearch contents / walk files / list dirs—
Where tools show up to the model Active tools are advertised in the system prompt's Available tools section and as API schemas each request. Custom tools get a one-line entry there only if you set promptSnippet; without it they're callable but invisible in that list. promptGuidelines adds behavior bullets to the Guidelines section — while that tool is active.

2Anatomy of a custom tool pi.registerTool

A tool is a plain object you hand to pi.registerTool() from an extension factory: metadata the model sees, a typebox schema its arguments are validated against, and an execute() that does the work and returns a result. That's the whole contract.

FIG 2 · the full registerTool contract
pi.registerTool({…}) — from an extension factorymetadata + schema + behavior, all in one object (fields below)
▼when the model calls it…
1 · prepareArguments(args)?optional — fix up old stored call shapes before validation (resumed sessions that predate a schema change); keep the public schema strict
▼
2 · validate against parameterstypebox schema; use StringEnum from @earendil-works/pi-ai for string enums (Google-compatible — Type.Union/Literal breaks Google)
▼
3 · tool_call event (can block — §3)
▼
4 · execute(toolCallId, params, signal, onUpdate, ctx)params are validated & typed · signal ⇒ cancellation (Esc) · onUpdate ⇒ stream progress · ctx ⇒ cwd, ui, session, exec…
▼return value ↓ or throw ↑ (throw = failure, reported to the model)
5 · result shape{ content, details, isError?, usage?, terminate? } — returning a value NEVER sets isError; only throwing does
▼
6 · tool_result event (can modify — §3)

The fields

FieldPurpose
name requiredunique id the model calls; must equal an existing name to override a built-in (§4)
labelhuman name shown in the UI
description requiredshown to the LLM — what it does & when. Your tool’s only documentation for the model.
parameterstypebox Type.Object schema — validated before execute
promptSnippetone-liner for the system prompt’s “Available tools” list (omitted custom tools stay out of that list)
promptGuidelinesbullets appended flat to “Guidelines” while the tool is active — must name the tool (“Use my_tool when…”, never “this tool”)
prepareArgumentsoptional pre-validation migration hook (§ FIG 2 step 1)
executethe work (§ below)
renderCall / renderResult / renderShelloptional custom TUI rendering (§7)

execute() signature

async execute(toolCallId: string, params: T, signal?: AbortSignal, onUpdate?: (update) => void, ctx: ToolContext) => Result

Result: what goes where

return {
  content: [{ type: "text", text: "Done" }], // → the LLM's context
  details: { items: [...] },                   // → TUI render + session state
  usage: nested.usage,   // optional: nested LLM usage for accounting
  terminate: true,       // optional: stop follow-up after this batch
};
  • throw an Error from execute ⇒ result marked isError: true and reported to the model. Returning a value never marks it an error.
  • onUpdate streams interim {content, details} while the tool runs (progress, partial results).
  • Check signal?.aborted to exit cleanly on Esc.
  • terminate: true only ends the turn when every finalized result in the batch also returns it.
  • Accept a path? Some models prefix @ — built-ins strip a leading @; normalize it in custom path tools too.

Minimal working tool

import { Type } from "typebox";
import { StringEnum } from "@earendil-works/pi-ai";

pi.registerTool({
  name: "todo",
  label: "Todo",
  description: "List or add items to the project todo list",
  promptSnippet: "List or add items in the project todo list",
  parameters: Type.Object({
    action: StringEnum(["list", "add"] as const),
    text: Type.Optional(Type.String()),
  }),
  async execute(_id, params) {
    if (params.action === "add") items.push(params.text!);
    return {
      content: [{ type: "text", text: "Added \"" + params.text + "\"" }],
      details: { count: items.length },
    };
  },
});
Schema rules that bite String enums must use StringEnum from @earendil-works/pi-ai — Type.Union/Type.Literal breaks Google’s API. Export your params type (export type MyToolInput = Static<typeof schema>) so tool_call handlers can narrow it (§3).

3Interception — events around every tool gates & middleware

Extensions subscribe to tool events with pi.on(). Two of them are the power tools: tool_call can block or rewrite a call before it runs (permission gates, argument patching); tool_result can read, patch or replace the outcome (logging, enrichment, summarization).

FIG 3 · the event sequence around one tool execution
tool_execution_start
▼
tool_call — interception point #1before the tool executes. event.input is mutable: earlier handlers' mutations flow to later handlers and into the real execution (no re-validation). Return { block: true, reason?, terminate? } to refuse.
▼only if not blocked
execute() runs
▼while running…
tool_execution_update fires as the tool streams progress (from onUpdate)
▼on completion…
tool_result — interception point #2after execution, before the result message. Handlers chain like middleware (extension load order), each seeing the latest result; return partial patches — { content?, details?, isError?, usage? } — omitted fields keep current values.
▼
tool_execution_end then the toolResult message enters the session

Guard rails & patching — tool_call

pi.on("tool_call", async (event, ctx) => {
  // narrow for typing (built-ins need no type params)
  if (isToolCallEventType("bash", event)) {
    event.input.command = `source ~/.profile\n${event.input.command}`;
    if (event.input.command.includes("rm -rf")) {
      return { block: true, reason: "Dangerous", terminate: true };
    }
  }
  // typed custom tools:
  if (isToolCallEventType<"todo", MyTodoInput>("todo", event)) {
    event.input.text = event.input.text?.trim();
  }
});

Notes: terminate only applies to a blocked call and stops the agent early when every finalized result in the batch is terminating. ctx.sessionManager is current up to this call; in parallel mode you won't see sibling results yet (they're preflighted sequentially, executed concurrently).

Middleware patching — tool_result

pi.on("tool_result", async (event, ctx) => {
  if (isBashToolResult(event)) {
    // event.details is typed: BashToolDetails
    const resp = await fetch("https://…/summarize", {
      method: "POST",
      body: JSON.stringify({ content: event.content }),
      signal: ctx.signal,        // Esc cancels your nested work too
    });
    if (resp.ok) {
      return { content: [/* summarized */], isError: false };
    }
  }
});

Use ctx.signal for nested async so user cancellation propagates. In parallel mode tool_result/tool_execution_end may interleave in completion order; final messages are emitted in source order.

user_bash — intercepting the human’s ! commands

Fires when the user runs !/!! (not the model). Three moves:

  1. Return custom operations — { operations: remoteBashOps } (e.g. run on SSH).
  2. Wrap pi’s local backend — createLocalBashOperations() then delegate after a tweak (e.g. source ~/.profile first).
  3. Full replacement — return { result: { output, exitCode, cancelled, truncated } } directly.

event.excludeFromContext is true for !!; event.cwd carries the working dir. user_bash commands never receive the PI_* session env that model-driven bash gets.

4Overriding built-ins same-name replacement

Register a tool whose name equals a built-in (read, bash, edit…) and you replace it — the classic pattern for read-only lockdowns, logging, or sandboxing. Interactive mode warns when this happens, so it's deliberate.

FIG 4 · what an override replaces (and what it inherits)
extension registers tool named read (etc.)via auto-discovery, settings extensions, or pi -e ./tool-override.ts
▼
name collision → built-in replacedinteractive mode shows a warning · --no-builtin-tools also works if you want no built-ins at all alongside extension tools
▼execution & rendering are resolved independently per slot…
execute: yoursyour code runs — wrap, gate, or reimplement. Must return the exact result shape incl. the built-in's details type (ReadToolDetails, BashToolDetails, GrepToolDetails, LsToolDetails, FindToolDetails…) — UI & session logic depend on it
rendering: inherited unless you opt outomit renderCall/renderResult → built-in renderer used (syntax highlight, diffs…). Define one → only that slot is yours. Perfect for wrap-with-logging without redoing UI
not inherited: prompt metadatapromptSnippet/promptGuidelines must be redefined on the override if you want them
Example in the wild examples/extensions/tool-override.ts replaces read with a logging + access-control wrapper; protected-paths.ts blocks writes to sensitive files; dirty-repo-guard.ts and git-checkpoint.ts wrap git state before/after work. Try pi -e ./tool-override.ts to feel the warning + swap.

5Remote execution & spawn hooks take tools elsewhere

Every built-in is built on a thin operations seam. Swap the operations and the tool runs against SSH, a container, a sandbox — without the model or the UI knowing. There are also factory helpers that return ready-made tools, and hooks to tweak how commands spawn.

FIG 5 · the operations seam
built-in tool = fixed logic + pluggable operationse.g. read = path logic + readFile(path)/access(path) ops; bash = spawn logic + BashOperations
▼two ways to use the seam…
factory + registercreateReadTool(cwd, { operations }), createBashTool(cwd, {…})… then pi.registerTool() the result (maybe swapped per-run by a flag)
reuse the local backendcreateLocalBashOperations() for user_bash — no need to reimplement process spawning/termination
▼
operations interfaces per toolReadOperations · WriteOperations · EditOperations · BashOperations · PowerShellOperations · LsOperations · GrepOperations · FindOperations — implement the few methods; wire each to SSH / Docker / HTTP

spawnHook — adjust every command before it runs

import { createBashTool } from "@earendil-works/pi-coding-agent";

const bashTool = createBashTool(cwd, {
  spawnHook: ({ command, cwd, env }) => ({
    command: `source ~/.profile\n${command}`,   // always source your profile
    cwd: `/mnt/sandbox${cwd}`,                   // jail into a sandbox
    env: { ...env, CI: "1" },
  }),
});
Session env & spawnHook ordering createBashTool()/createPowerShellTool() inject PI_SESSION_ID, PI_SESSION_FILE, PI_PROVIDER, PI_MODEL, PI_REASONING_LEVEL into each command before the hook runs, so the hook sees them in env. Opt out with exposeSessionEnvironment: false. (Full story in the env-vars section of the customization guide.)

Working example: examples/extensions/ssh.ts routes read/bash/etc. over SSH behind an --ssh flag; bash-spawn-hook.ts is the minimal hook demo; sandbox/ and gondolin/ show container sandboxing setups.

6Truncation discipline the #1 rule

Custom tools must truncate their output. Pi’s hard ceiling is 50KB (~10k tokens) or 2000 lines, whichever comes first — blow past it and you risk context-overflow errors, compaction failures, and a degrading model. Pi exports the exact utilities it uses, so there's no excuse to hand-roll.

FIG 6 · the truncation flow every output-producing tool should follow
capture raw outputrun the command / read the source
▼
choose a head or tail strategytruncateHead() when the beginning matters (file reads, search hits) · truncateTail() when the end matters (logs, command output) · truncateLine() for a single huge line
▼truncate with the same limits pi uses
applytruncateHead(output, { maxLines: DEFAULT_MAX_LINES, maxBytes: DEFAULT_MAX_BYTES }) → { content, truncated, outputLines, totalLines, outputBytes, totalBytes }
▼if truncated…
park the full output + tell the modelwrite the full text to a temp file (writeTempFile) and append a note: [Output truncated: N of M lines (A of B). Full output saved to: <file>]
▼
return the bounded resultand document the limits in your tool description
import { truncateHead, formatSize, writeTempFile,
         DEFAULT_MAX_BYTES, DEFAULT_MAX_LINES } from "@earendil-works/pi-coding-agent";

const raw = await runCommand();
const t = truncateHead(raw, { maxLines: DEFAULT_MAX_LINES, maxBytes: DEFAULT_MAX_BYTES });
let text = t.content;
if (t.truncated) {
  const f = writeTempFile(raw);
  text += `\n\n[Output truncated: ${t.outputLines}/${t.totalLines} lines` +
          ` (${formatSize(t.outputBytes)}/${formatSize(t.totalBytes)}). Full output saved to: ${f}]`;
}
return { content: [{ type: "text", text }], details: {} };

Copy-paste example: examples/extensions/truncated-tool.ts wraps rg properly. formatSize gives human “50KB / 1.5MB” strings.

7Custom rendering in the TUI renderCall / renderResult

Tool rows in the transcript are just components. Give your tool renderCall and/or renderResult and you control exactly what the user sees while the tool runs and after it settles — while the model still reads plain content. Rendering never touches the LLM; it's pure UI.

FIG 7 · how a tool row is drawn
call begins → renderCall(args, theme, context)header line: tool name + the arguments, styled
▼streaming updates…
renderResult(result, {expanded,isPartial}, theme, context)called repeatedly as onUpdate arrives (isPartial: true) and finally when settled; expanded = user pressed ctrl+o
▼
wrapped in a themed Box (padding/background) — unless renderShell: "self"self-shell = you own framing & background (big previews that must stay visually stable)
▼slot renderer missing or throws → graceful fallback
fallbacksrenderCall → tool name only · renderResult → raw text of content

context — what your renderers receive

  • args — current tool-call arguments (read here, don't copy into state)
  • state — row-local object shared across renderCall & renderResult
  • lastComponent — previous component for this slot (reuse & mutate in place)
  • invalidate() — request a re-render of this row
  • toolCallId, cwd, executionStarted, argsComplete, isPartial, expanded, showImages, isError

Patterns & best practice

  • Use Text with padding (0,0); the default Box handles padding.
  • \n for multi-line; keep the collapsed view compact; add detail when expanded.
  • Handle isPartial (e.g. a “Processing…” line) for streaming feedback.
  • Empty slot? Return an empty Container.
  • Color via theme.fg(token, text) — semantic theme tokens, never hardcoded colors.
  • Keybinding hints that respect the user's config: keyHint("app.tools.expand", "to expand") (also keyText, rawKeyHint).
renderResult(result, { expanded, isPartial }, theme, context) {
  if (isPartial) return new Text(theme.fg("warning", "Processing…"), 0, 0);
  if (result.details?.error) return new Text(theme.fg("error", `Error: ${result.details.error}`), 0, 0);
  let text = theme.fg("success", "✓ Done");
  if (expanded && result.details?.items)
    for (const item of result.details.items) text += "\n  " + theme.fg("dim", item);
  return new Text(text, 0, 0);
}

Components come from @earendil-works/pi-tui (Text, Box, Container…). Full component API lives in docs/tui.md; see examples/extensions/built-in-tool-renderer.ts and tool-execution.ts (source) for how rows compose. Built-in override renderers inherit per slot (§4).

8Dynamic tools — tools that load tools scale past the prompt

Register a thousand tools? The system prompt can’t hold them. Instead: register everything, keep a small set active, and let a loader tool switch on more tools mid-task by editing the active set. Pi detects additive changes, records them on the loader's result, and (on capable models) uses native deferred loading so the prompt prefix stays cacheable.

FIG 8 · the loader pattern
register EVERY toolpi.registerTool() for all — they're now in pi.getAllTools() but not yet offered to the model
▼
keep only a few activeloader stays active (e.g. search_tools); the rest inactive (e.g. lookup_weather, search_issues)
▼task needs a dormant capability → model calls the loader
loader runs: pi.setActiveTools([…current, …matching])additive only — don't remove active tools in the same call. Names must already be registered (unknown ones ignored). Match by keyword, BM25, embeddings, remote catalog…
▼
pi records the additions on the loader's tool resultapplied before the next model request — no special return needed; the active-tool change IS the signal
▼delivery strategy depends on the model…
native deferred loadingAnthropic Sonnet/Opus/Fable ≥ 4.5 (no Haiku): defer_loading + tool_reference at the load point · OpenAI gpt-5.4+: completed client tool_search_call/tool_search_output. Stable prompt prefix preserved
fallback (all other models)pi resends the full active list next request — works everywhere, but adding definitions may invalidate the provider's cached prompt prefix
Caching caveats that decide your design
  • Removals work but never use deferred loading — prefer keeping the loader active and only adding.
  • A tool with promptSnippet/promptGuidelines triggers a system-prompt rebuild when activated, which can break the prefix cache even on deferred-capable models → lazily loaded tools should rely on their description and skip prompt metadata.
  • Verified proxies/custom models can opt in per-provider: compat.supportsToolReferences: true (anthropic-messages) or compat.supportsToolSearch: true (openai-responses / openai-codex-responses). Leave off unless the endpoint truly supports it.

Managing the active set from anywhere

pi.getActiveTools(); // ["read","bash",…]

pi.getAllTools(); // full metadata: name, description,
//   parameters, promptGuidelines, sourceInfo
// sourceInfo.source: "builtin" | "sdk" | extension source

// read-only mode:
pi.setActiveTools(["read", "bash"]);
// add without dropping anything:
pi.setActiveTools([...new Set([...active, "my_tool"])]);

These work for built-ins too, so a command or another extension can switch modes at runtime. Tools that enter via the SDK (createAgentSession({ customTools })) report source: "sdk". Works with every model — only the delivery mechanism differs (§ FIG 8).

Full search-tool example: examples/extensions/dynamic-tools.ts. The two-games-in-one demo (snake.ts / space-invaders.ts) also shows selective activation.

9State & file-safety things that bite in parallel

Two failure modes await every serious custom tool — and pi ships the remedies. One: multiple tools editing the same file in parallel can silently lose writes. Two: your tool's state must survive forks, resumes and reloads.

withFileMutationQueue — join the same per-file queue as edit/write

FIG 9 · the lost-update race, and the fix
the racetool calls run in parallel by default. Custom tool A reads foo.ts while built-in edit also changes foo.ts in the same turn → both computed from the original → whichever write lands last overwrites the other's change. Silently.
▼the fix
queue the whole mutation window on the real file pathwithFileMutationQueue(absolutePath, async () => { …read-modify-write… }) — same queue built-in edit/write use, so A and edit serialize
▼rules…
pass the resolved path, not the raw argumentresolve absolute relative to ctx.cwd first. Existing files are canonicalized via realpath() (symlink aliases share one queue); new files fall back to the resolved absolute path. Queue read-modify-write logic, not just the final write.

State: session-aware, branch-safe

Where does your tool keep data between calls?

in-memory variablesfine within one run — but lost on reload, resume, fork, or process exit
tool-result detailsthe docs' rule: store state in details so it rides the session — branches carry it correctly; rebuild on session_start by scanning the branch's toolResult messages
multiple tools, one stateone extension closure = shared state between db_connect/db_query/db_close; clean up on session_shutdown (close the pool!)
// State that survives forks & resumes: snapshot it into details each call…
let items: string[] = [];
pi.on("session_start", async (_ev, ctx) => {          // …and rebuild from the branch
  items = [];
  for (const e of ctx.sessionManager.getBranch())
    if (e.type === "message" && e.message.role === "toolResult"
        && e.message.toolName === "my_tool")
      items = e.message.details?.items ?? [];
});
// …then in execute: return { content: [/*…*/], details: { items: [...items] } }
Usage accounting for nested LLM calls If your tool calls an LLM internally, return the combined usage on the result — pi persists it on the tool result and folds it into footer totals, /session, and RPC totals. tool_result handlers can inspect or replace it.

The 30-second summary
  1. Register tools with pi.registerTool(): schema (Type) + metadata (description/promptSnippet) + execute() returning {content, details}.
  2. Guard & patch around every call with tool_call (block/mutate) and tool_result (middleware patches).
  3. Mutate files through withFileMutationQueue; truncate output to 50KB/2000 lines; keep state in details.
  4. Override built-ins by name (renderers inherit per slot); route them remotely through operations; renderCall/renderResult for bespoke UI; setActiveTools for tool-scale.
